# Release and versioning policy

Canonical rules for version numbers, release pacing, pre-release retention and release notes.
They apply to every maintainer, contributor and agent. The mechanics of cutting a release live in
[`docs/releases/process.md`](../../docs/releases/process.md); the reasons behind these rules are recorded in
[ADR 0006](../../docs/architecture/adr/0006-release-versioning-and-prerelease-retention.md).

## Version numbers

1. Versions follow [Semantic Versioning 2.0.0](https://semver.org/) as `MAJOR.MINOR.PATCH`. Tags are `vMAJOR.MINOR.PATCH`.
   Four-part versions such as `0.9.3.1` are not valid SemVer and are refused by the release workflow.
2. Before `1.0.0`, `feat:`, `fix:` and `perf:` commits increment the patch, and breaking changes increment the minor
   (`bump-minor-pre-major` and `bump-patch-for-minor-pre-major` in `.github/release-please/release-please-config.json`).
3. A published version is never modified, re-tagged, reused or lowered. A mistake is corrected by a new, higher version.
   The version line only moves forward: `0.9.4` follows `0.9.3`, and the project does not restart at `0.1.0`.
4. `0.y.z` is initial development, where anything may change. Reaching `0.9` quickly is not a reason to renumber.
5. `1.0.0` declares the public API stable. It is cut deliberately, not by accumulation. Before it, the maintainer confirms
   in the release PR that:
   - the HTTP API ([`docs/reference/api.md`](../../docs/reference/api.md)) and the database migrations are documented
     and upgrades from the previous release have been exercised;
   - the manual keyboard and screen-reader pass owed in [`DESIGN.md`](../../DESIGN.md) has been done;
   - the release and update path has been verified end to end on a stable (non-pre-release) release.

   The maintainer may amend this list in a pull request that updates this policy.

## Pacing

1. Ordinary releases follow the monthly cycle: Release Please opens or updates one release PR on the first day of each
   month (UTC), collecting everything merged since the previous release.
2. An off-cycle release is allowed only for a security fix, a data-integrity fix, or a defect in the release or
   install path itself. The release PR states which one applies. A finished feature is not a reason.
3. Ordinary pull requests never publish a release. Merging the release PR is the only action that tags and publishes.
4. Changes are verified on `main` before the release PR is merged. Release candidates are not published.

## Pre-releases and retention

1. While `prerelease: true` is set in the Release Please configuration, every `0.y.z` GitHub release is a pre-release.
   Pre-releases are not served by `releases/latest`, so the desktop updater endpoint and the `latest` and `stable`
   container tags do not move to them. Removing `prerelease` is a maintainer decision recorded in a pull request.
2. A release numbered `vMAJOR.MINOR.PATCH` is permanent history. It is not deleted or re-tagged.
3. Release candidates (`-rc.N`) and draft releases are temporary. Once a numbered release supersedes them and the
   changelog records what they carried, they may be removed together with their tags. The removal is listed in the
   pull request that records the retention decision, and the notes are backed up first.
4. Container images and their keyless signatures are not deleted: the signatures live in a public transparency log.
5. Links in the changelog and release notes point only at tags that exist. Where a tag has been removed, point at the
   superseding release or at a commit range.

## Changelog and release notes

1. `docs/releases/CHANGELOG.md` is generated by Release Please from Conventional Commits. Commit subjects are written as
   release-note lines: English, imperative, user-visible.
2. In the release PR, the maintainer edits the new section into the house style: a one-sentence summary, a short
   **Highlights** list written for users, and the generated lists below it. Section headings keep the
   `## [x.y.z](compare-url) (date)` format so Release Please can keep prepending.
3. The GitHub release body is produced from [`docs/releases/release-notes.template.md`](../../docs/releases/release-notes.template.md)
   with `pnpm run release:notes -- vX.Y.Z`. It always states whether the release has database migrations, lists the
   assets and the container image, and links the full commit range.
4. Hand-written highlights live in `docs/releases/highlights/<version>.md`. The generator includes the file when it exists
   and falls back to the grouped commit list when it does not.
5. Notes are in English. A correction to published notes is made with `gh release edit` and recorded in a docs pull request.

## Approvals and review

1. The release PR is merged by a maintainer after the required checks pass.
2. Publication of container images and assets waits for approval in the `release` GitHub environment. A reviewer other
   than the author of the change approves when one is available.
3. Changes to release workflows, the updater, signing or provenance need independent review under
   [`agent-collaboration.md`](agent-collaboration.md). Documentation and the notes generator do not change release
   behavior and follow the normal pull request flow.
4. After publication, verify the assets, `SHA256SUMS`, the notes and the platform labels, as listed in the process document.

## Rollback

1. A bad release is not deleted. Publish a fixed higher version and add a warning line to the notes of the bad one.
2. A release that was published but never received its assets (for example, publication was not approved) may be
   completed or cancelled. Rebuilding assets with the `Release` workflow always builds the commit its tag points to.
3. Moving a published tag to a newer commit is not allowed.
